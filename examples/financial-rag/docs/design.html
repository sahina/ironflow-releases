Ironflow example app · design

Financial documents,
answered and checked

A RAG app where a new batch of documents is treated like a deploy: shadowed, tested against a golden set, then promoted or rolled back.

In one paragraph

Every 15 minutes it hashes a folder of financial filings and ingests anything new. Claude reads each PDF and pulls out prose, table rows, and a plain-English summary of each table. Those land in an index that nobody can query yet. An eval runs ~30 known questions against that shadow index. Only if it scores well does the live pointer move. If the flip fails, a saga puts it back.

Most RAG demos stop at it returned something. The interesting part here is the last step: the system refuses to publish an index that got worse. That gate is a workflow, not a script, so it retries, resumes after a crash, and leaves an audit trail.

Scope

Runs locally inside an Ironflow checkout, against a locally built SDK. Publishing it as a standalone downloadable is deliberately deferred.

The loop

Five stages. The dashed box is the one that makes this different from a normal ingest pipeline.

W1Poll Hash the folder. Skip anything unchanged.
→
W2Parse Claude reads the PDF. Facts become events.
→
shadowIndex vn+1 Embedded and searchable, but not live. Nothing queries it yet.
→
W3Eval ~30 known questions, scored three ways.
→
W4Promote Move the live pointer — or compensate and roll back.
Why it matters

A bad filing, a changed chunking strategy, or a model regression cannot silently degrade answers. It has to pass the gate first.

Two databases, one rule

One Postgres server, two databases. The application never opens a socket to Ironflow's. This is a hard tenant, not a preference.

ironflow

Owned by Ironflow. Reached only through the SDK.

  • Event streams — the write model
  • Three SQL projections: documents, tables, index state
  • Run and step history

ragapp

Owned by the example. Its own connection pool.

  • chunks — pgvector embeddings + full-text
  • index_pointer — which version is live
  • Everything vector-shaped lives here
Workflow reads and writes Ironflow only via step.* and client.*
→
External projection the one component that bridges: reads events, writes ragapp
→
Retriever queries ragapp directly with its own pool

Ironflow never stores a vector. That is what keeps the boundary honest — the moment the app needs pgvector, it uses its own database rather than reaching into the platform's.

Four workflows

All four run in pull mode (createWorker). Dots: ● work, ● wait, ● emit, ● compensate.

W1 · pollSource

Trigger: cron, every 15 minutes

  • hash-sourceHash every file in the folder. Content hash, not mtime — a touched file is not a changed file.
  • diff-seenCompare against what has already been ingested. Unchanged files stop here and cost nothing.
  • open-batchAllocate the next index version. This batch's documents will land in it, invisible to queries.
  • emit DocumentVersionCreatedOne event per changed file. Each fans out to its own W2 run.
  • await-parsesDurable sleep, then count how many reported done. Repeat until the batch is complete.
  • close-batchEmit IngestBatchClosed, which is what starts the eval.

W2 · parseDocument

Trigger: DocumentVersionCreated · one run per document

  • split-pagesCut the PDF into page ranges. A document block has no page-range option, so the cut has to be physical.
  • extractClaude reads each range natively as a PDF and returns structured prose, table rows, and table summaries.
  • emit-artifactsOne event per artifact, with IDs derived from its own coordinates so a retry cannot duplicate anything.
  • emit DocumentParsedTells W1 this document is done.

W3 · runEval

Trigger: IngestBatchClosed

  • load-goldenRead the golden set — questions with known-correct answers.
  • score-retrievalDid the right chunk come back at all? Cheap, no model call.
  • score-numericIs the figure exactly right? This is the tier that actually matters for finance.
  • score-agentRun the real agent end to end, including the citation gate.
  • emit EvalVerdictPass or fail, with the failing question IDs attached.

W4 · promoteIndex

Trigger: EvalVerdict · saga with compensation

  • check-verdictFailed? Stop here. The shadow index stays shadowed and the live one is untouched.
  • advance-pointerMove the live pointer to the new version. This is the only moment users see new data.
  • verify-liveRe-ask one golden question against the now-live index.
  • compensateIf verification fails, put the pointer back. The rollback is a step, so it is durable too.

Splitting a filing three ways

A financial PDF is not one kind of content, so it is not stored as one kind of record.

kind: proseNarrative Management discussion, notes, risk language. Embedded whole.
kind: table_rowTable rows Kept as structured numbers, queried with SQL. Never summarised into text and then re-parsed.
kind: table_summaryTable summaries One plain-English sentence per table, embedded so semantic search can find the table.
Why the summary exists

Nobody asks "row 4 of the operations statement". They ask "what was revenue". The summary is what search matches; the rows are where the number is read from. Two hops, each doing what it is good at.

Restatements

Companies re-file. The same entity and period can appear twice with different numbers, and the later filing wins.

2024-11-01Original Revenue 1,284,000
→
2025-02-14Restated Revenue 1,251,000 — this is the answer
→
Both kept A restatement is a new version, never a delete. The old figure stays auditable.

Retrieval

Vector search alone is bad at finance. Tickers, line-item labels and acronyms are exact tokens — semantic similarity blurs exactly the thing you need to match. So both run, and the scores are blended.

semanticVector voyage-finance-2, 1024 dimensions. Finds meaning.
lexicalKeyword Postgres full-text. Finds exact tokens.
→
Blended + scoped Filtered to the live index version, superseded filings dropped.

Reranking is left in as a commented, optional step. It helps, it costs a model call per query, and the example is clearer without it turned on.

The eval is the point

Three tiers, cheapest first, because they fail for different reasons and you want to know which.

TierQuestion it answersCost
RetrievalDid the right chunk come back at all?No model call
NumericIs the figure exactly right?No model call
AgentDoes the full loop answer correctly, with a citation?Full agent run

A retrieval failure means chunking or embedding broke. A numeric failure with retrieval passing means table extraction broke. An agent failure with both passing means the prompt or the tools broke. One number would have told you none of that.

Passes Pointer advances. New documents become queryable.
→
Fails Pointer does not move. The previous index keeps serving. Failing question IDs are reported.
Ground truth

The corpus is generated, not downloaded. Because the figures are authored, the golden set is exactly correct instead of eyeballed off a real PDF — which matters when the whole point is measuring correctness. Swapping in real SEC filings is a documented one-step change.

Decisions worth knowing

ChoiceReason
Extracted data lives in Ironflow streams and projectionsOne database, real CQRS. The app never touches Ironflow's Postgres directly.
Vectors live in the app's own databaseIronflow has no vector support, and adding one for a demo would break the tenant.
Native PDF into ClaudeNo OCR stack, no layout parser. Page ranges are cut physically first.
Structured output over citationsThe two cannot be combined, so page numbers ride inside the extraction schema.
Shadow index + pointer flipMakes promotion atomic and rollback a single write.
Eval as a workflow, not a scriptGets retries, crash-resume and history for free.
Synthetic corpus by defaultExact ground truth, and the example runs immediately.
Pull mode, not pushLoad-bearing: push-mode step storage collides on repeated step names, which breaks multi-turn agents on resume.

Scope

Built

  • Four workflows, three SQL projections, one external vector projection
  • An agent with four tools and a citation gate
  • A golden set with a three-tier scorer
  • Unit tests on the logic where a silent bug produces a plausible wrong number

Not built

  • Standalone publishing. Runs in-repo only, for now.
  • CI wiring. Tests are human-run.
  • Reranking. Present as a commented, optional step.
  • Index scale-up. The demo corpus is small enough that search is a full scan; the production pattern is documented, not implemented.
Known risk

The eval gate is only as good as the golden set. Thirty questions catch gross regressions, not subtle ones. Growing the set is the honest way to make the gate stronger — there is no clever substitute.
