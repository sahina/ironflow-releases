examples/travel-booking

Book a trip. Then break it.

A booking app where a flight and a hotel are reserved as one unit of work — and five ways it can go wrong, each one showing a different thing Ironflow does about it. Every screen and every line of code is on this page. You do not need to run anything.

How to read a beat

Each beat is a sequence of moments. On the left is the screen at that moment. On the right is what just happened inside the engine, and the code that did it.

Point at the screen, then read across. That is the whole format.

Want to run it for real? README.md, next to this file. But the page stands alone.

The app · one screen, four zones

Everything happens in view

Deliberately one page. You need to see the button that breaks things and the thing it breaks at the same time — otherwise the demo is two windows and a story about what happened in the other one.

Left · pick a trip

Three flights, three hotels. Seat and room counts are live — they move when anyone books, with no refresh. UA 100 has one seat; that is beat 4's whole plot.

Centre · the journey

The three steps of a booking, lighting up as they happen — and striking through when they get undone.

Right · chaos, and the bottom bar

Buttons that break things on purpose, plus two status lights. Along the bottom, a scrubber over any booking's recorded history.

How it works · show this once

Four moving parts, and nothing hidden

Every beat that follows is a variation on this one picture, so it is worth thirty seconds up front.

Write side

Nothing is updated in place. Every change is an event appended to a stream. That is what makes beats 2, 3 and 5 possible at all.

Read side

Projections fold those events into state the UI can render. The browser subscribes; the server pushes. Seat counts move on their own.

Why it matters

Split write from read and rollback, crash-resume and time travel arrive as consequences — not as features someone had to build.

Beat 1

A trip books cleanly

The boring one, and it goes first on purpose. Everything after this is these same three steps refusing to go to plan.

01Before anyone clicks

Those seat counts were not hard-coded into the page. On load, the browser asks for the availability projection and then subscribes to it — so any change anyone makes arrives as a push. 

await ironflow.subscribeToProjection("availability", {
  onUpdate: (state) => setAvailability(state),
});
app/page.tsx:58

02Book trip — the steps run in order

The click emits one event. A function picks it up and works through three steps. Each step.run() is durable: the moment it succeeds, its result is written down. Notice the seat count already dropped to 5 — step 1 committed, and the projection pushed. 

await step.run("reserve-flight", async () => {
  await holdInventory({ ... });
  return appendBooking(stream, FlightReserved, {...});
});
worker.ts:79 — then :108 for the hotel, :137 for the card

03Confirmed

A final step appends booking.confirmed. Nothing here was a database update — the booking's whole life so far is a list of appended facts, which is exactly why beat 5 can replay it. 

await step.run("confirm-booking", async () =>
  appendBooking(stream, BOOKING_EVENTS.Confirmed, { bookingId }));
worker.ts:160
The point Three steps, each one written down as it succeeds, and a read model that updates itself. That single property — durable, memoized steps — is what every beat from here on exploits.
Beat 2

The card declines, and the trip un-books itself

A flight is held. A room is held. Then payment fails — and now you owe the customer an apology and two cancellations.

01Arm the failure

The chaos panel flips a flag in the worker process. Nothing is faked further down — the payment step will genuinely throw, and the engine will genuinely fail the run. 

if (paymentMode === "fail") {
  // NonRetryableError, not a bare throw: skips the retry
  // schedule so the rollback happens now, not after backoff.
  throw new NonRetryableError("Card declined.");
}
worker.ts:141–145

02The dangerous moment

This is the state every booking system fears: two real reservations held, and no money. Left alone, that seat is dead inventory nobody can sell. This is the problem Ironflow is about to solve on its own.

Worth pausing here when presenting. The audience needs to feel the problem before they can appreciate the next frame.

03It undoes itself, backwards

Step 2 strikes through before step 1 — compensations run in reverse, the way undo has to. Nobody wrote a rollback routine: each step registered how to undo itself when it ran, and the engine called those in order. 

await step.run("reserve-flight", /* … */);
step.compensate("reserve-flight", async () => {
  await releaseInventory({ ... });
});
worker.ts:94 — and :123 for the room, :153 for the refund
The point This is the saga pattern, and it is a first-class primitive rather than a try/catch you maintain by hand. step.compensate() is the entire mechanism.
Beat 3

Kill the server mid-booking

Not a graceful shutdown. kill −9, while step 3 is in flight, with two reservations already held.

01Catch it in the act

Slow payment holds step 3 open for eight seconds — just a setTimeout, there to give you a window to kill the process in. 

if (paymentMode === "slow") {
  await new Promise((r) => setTimeout(r, SLOW_PAYMENT_MS));
}
worker.ts:138–140

02Crash worker — the process is gone

A real process.exit(1), not a simulation. The status light goes red and the journey stops moving. Two reservations are held by a run that no longer has anything executing it. 

case "/crash":
  res.end(JSON.stringify({ ok: true }));
  setTimeout(() => process.exit(1), 50);
worker.ts — chaos control server

03The wait — say the real number

A supervisor restarts the worker in about a second. The run takes about two minutes, because the engine will not hand it to a different worker until the previous one's capacity lease lapses — and that is 90 seconds, with no external knob. 

LeaseExpiry: 90 * time.Second
internal/capacity/config.go:37 — measured on this example, not estimated

04It picks up where it left off

A fresh process finishes a booking it never started. Steps 1 and 2 are replayed from their recorded results rather than executed again — no second seat, no double charge. That is memoization, and it is why recording: true matters. 

createFunction({
  id: "book-trip",
  recording: true,   // keep the history
}, async ({ step }) => { /* … */ });
worker.ts:53, :60
Present this as a talking beat, not a waiting beat Two minutes is a long silence. Start it, walk through beats 4 and 5 while it recovers, then come back to the confirmed trip. The guarantee is worth the wait; the silence is not.
Beat 4

Two travellers, one seat

The oldest bug in booking software: sell the same seat twice because two requests checked availability at the same moment.

01One seat, two people who want it

The count comes from folding the flight's event stream — capacity minus every hold, plus every release. The same fold runs in the projection and in the booking function, deliberately, so the two can never disagree about what is left. 

export function seatsLeft(state, flightId) {
  const f = state?.flights?.[flightId];
  return f ? f.capacity - f.held : 0;
}
domain.ts — shared by worker.ts and the UI

02Both check, both are told yes

Both read the stream at version 41. Both see a free seat. Both try to append. The append carries the version it expects, so the store accepts the first and rejects the second — no lock, no queue, no mutex in application code. 

try {
  await ironflow.streams.append(streamId, event, {
    expectedVersion: info.version,      // ← the race
  });
} catch (err) {
  if (isVersionConflict(err))
    throw new NonRetryableError(soldOutMessage);
  throw err;
}
worker.ts:200–224

03One booking, one apology, no double-sell

The loser's saga fails and compensates — exactly the machinery from beat 2, arriving here for a completely different reason. Bob gets a clear message and no charge. The seat was never sold twice, because the database would not allow it.

Beats 2 and 4 are the same mechanism seen from two angles. Worth saying out loud — it is the moment the design clicks for most people.

The point Correctness under contention lives in the store, not in careful application code. You do not have to remember to be careful; the append refuses to be wrong.
Beat 5

Rewind any booking

The question every one of these beats has been building toward: when this goes wrong at 3am in production, what can you actually see?

01Ask for the run's history

One call, by run id. This works for any booking on the page — the confirmed one, the rolled-back one, the one that lost the race. 

const events = await ironflow.getRunTimeline(runId);
app/page.tsx:175

02Drag it, and collect the earlier beats

Every beat left a trace here. This is where you prove the claims you made rather than asking the audience to take your word.

Scrub toand you can show
step.completed ×3the happy path — beat 1

The point Because every step was an appended fact rather than an in-place update, the run's whole history is still there. Time travel isn't a feature bolted on top — it is what you get for free once nothing overwrites anything.

If someone asks what's fake

The payment provider. That's it. The offline queue used to be on this list — it was twenty lines of localStorage in the demo — but v0.28.0 shipped a real IndexedDB outbox in the browser SDK, so the demo now uses createClient({ offlineQueue }) like any app would. Everything else is the real engine: real entity streams, a real version conflict, a real kill −9.

If someone asks about scale

Seat holds take the version of the whole flight stream, so two bookings on one flight serialise even when there is room. Fine for a demo; a real system would use per-seat reservation records. It is flagged in the code, not hidden.

Everything here is reproducible: examples/travel-booking/README.md has the five setup commands, and scripts/demo-saga-rollback.sh asserts beat 2 end to end.
